## 0. 확정된 결정 (전부 사용자 지정)

| # | 결정 | 내용 |
|---|---|---|
| 1 | **배포 형태** | 개인별 PC에 UI + 전략 엔진 설치. **계좌·API키·주문은 사용자 PC 밖으로 안 나간다** |
| 2 | **전략 배포 방식** | **L2 = 암호화된 코드 배포**. 서버가 기동 시 전략 모듈을 내려주고 로컬에서 실행 |
| 3 | **라이선스** | **기부금 방식**(판매·구독 아님). 결제 연동·만료 강제·기기 바인딩 전부 없음 |
| 4 | **키움 API** | 사용자 각자 발급·사용. 개발자가 타인 자격증명을 보유하지 않는다 |
| 5 | **조건검색식** | **사용자가 자기 HTS에 동일하게 4개를 만든다**. 이름도 동일 |
| 6 | **에러 안내** | 설치 UI에서 심플하게 요약 표시 |

### 왜 L2인가 (L1/L3를 안 고른 이유)

| | 서버가 주는 것 | 코드 보호 | 지연 | 조건검색 |
|---|---|---|---|---|
| L1 파라미터만 | 상수값 | ✕ 코드가 PC에 그대로 | 0 | 사용자 것 |
| **L2 암호화 코드** ← 채택 | 암호화된 전략 모듈 | △ 문턱만 높임 | 0 | 사용자 것 |
| L3 시그널 | "종목 X 매수" 신호 | ○ | +50~150ms | **서버 것** |

- **L3를 뺀 이유**: 조건검색식이 서버 계정 것이 되어 「조건검색 선택가능」 UI 항목과
  정면 충돌한다. 또 신호 배포는 법적 성격이 달라진다.
- **L1을 뺀 이유**: 코드 보호가 전혀 안 된다.
- ⚠️ **L2도 절대 보호가 아니다.** 파이썬 난독화(PyArmor/Cython/Nuitka)는 리버싱
  문턱을 높일 뿐이다. **실질적인 lock-in은 코드가 아니라 "매일 갱신되는 파라미터 +
  지속 업데이트"에서 나온다** — 지금 매일 하는 실측 분석이 진짜 자산이다.

## 1. 아키텍처

```
 [서버]                              [사용자 PC · 각자]
 ┌────────────────┐              ┌──────────────────────────┐
 │ 기부 키 → 만료일   │◄─── 조회 ────│ UI (설정·관제·수동매매)      │
 │ 전략 파라미터 배포 │───── 배포 ──►│ 전략 엔진 (L2 암호화 배포)     │
 │ 전략 코드 배포(L2) │              │ 키움 REST/WS ← 개인 계좌     │
 │ 조건식 편입 종목   │───── 대조 ──►│ SQLite (Postgres 대체)     │
 │ (자동 검증용)     │              │ 자격증명: Windows DPAPI    │
 └────────────────┘              └──────────────────────────┘
```

- 계좌·API키·주문은 **한 번도 서버로 안 간다**
- 서버의 「조건식 편입 종목」은 사용자 조건식이 원본과 같은지 **자동 대조**하는 용도
  (4장 참고). 서버가 이미 자기 봇을 돌리므로 **추가 비용 0**

### 🔴 아키텍처와 무관한 구조적 한계: 동시 매수

L1/L2/L3 어느 걸 골라도 **모두가 같은 전략·같은 조건식을 쓰면 같은 틱에 트리거된다.**

실측 근거: 평균 1틱 체결금액이 종목당 30만~300만원(08-02 기록). 사용자 50명 ×
180만원 = **9,000만원이 한꺼번에** 들어가면 30~300틱 분량이라 **가격을 밀어올린다.**
저유동성 종목(08-03 090710은 평균 1틱 41만원)이면 더 심하다.

완화책 — 설계에 **미리** 넣어야 하는 것:
- 사용자별 후보 순위 셔플 + 진입 시각 지터(0~3초 랜덤)
- 종목당 동시 진입 사용자 수 상한
- 유동성 하한 상향(지금 3천만/60초)
- 궁극적으로 **사용자 수 상한**

⚠️ 기부금 방식이라 당분간 사용자가 적을 것이므로 즉시 문제는 아니다. 다만
**늘어나면 반드시 터지는 항목**이라 지금 기록해 둔다.

### 9번 설계 함정 — 반드시 읽을 것

지금은 전부 **비율** 기반이다 (`strategy_manager.py:4649` `if gross_rate <= STOP_LOSS_RATE:`).
금액으로 바꾸면:

- **매수금액이 클수록 손절이 얕아진다.** -3만원 손절이면 200만원 매수 시 -1.5%,
  50만원 매수 시 -6%. 종목마다 손절 폭이 달라져 전략 일관성이 깨진다.
- 지금 캡 체계는 **왕복 수수료 0.23%**를 전제로 튜닝돼 있다. "1만원 익절"로 두면
  수수료도 안 나오는 값이 될 수 있다.

→ **권고: 금액으로 입력받되 내부는 비율로 환산하고, 환산된 %를 UI에 즉시 같이 보여줄 것.**
   최소값 가드(수수료 × 2) 필수.

| # | 조합 | 결과 |

| 1 | **눌림목자동 해제** | `PULLBACK_MAX_SLOTS`가 유니버스를 못 받아 논다. `MAX_HOLDINGS` 6인데 1A 캡이 4면 **실질 슬롯 4개**. 사용자가 "왜 6종목까지 안 사지?"라고 물어본다 |

## 6. Phase 계획 ← 실제 작업 시 이 장만 보면 된다

### 접근 원칙: 「전체 프레임」이 아니라 「바꾸기 비싼 3개」만 먼저

**먼저 확정해야 하는 것** (나중에 바꾸면 여러 곳을 다시):

| # | 항목 | 왜 |
|---|---|---|
| 1 | **설정 스키마** — 어떤 값이 사용자 조정 가능한가 | UI·서버 파라미터 배포·저장 형식이 **전부** 여기 의존. 이 프로젝트엔 이미 「매수금액 3곳」 사고 사례가 있다 |
| 2 | **SQLite 스키마** | 사용자 데이터가 쌓이기 시작하면 마이그레이션 부담이 영구히 따라온다 |
| 3 | **L2 패키징 경계** | 어디까지 암호화할지가 모듈 구조를 정한다. 나중에 바꾸면 import 구조를 다시 |

이 3개는 **코드가 아니라 문서로** 1~2세션이면 끝난다.

**전체 프레임을 다 짜면 안 되는 이유**
- **실거래 중이다.** 큰 리팩터링을 한 번에 하면 봇을 멈추거나 두 버전을 유지해야 한다
- 이 프로젝트의 검증 문화(테스트 1,421건 + 매일 실측)는 **점진적 변경에 최적화**돼 있다.
  덩어리로 바꾸면 "무엇이 무엇을 깼는지"가 안 갈린다
- UI는 **써봐야 안다.** 10화면을 다 설계해두면 3개 쓰고 나서 7개를 다시 그린다

**완전 점진적도 안 되는 이유**
설정 스키마를 안 정하고 UI부터 만들면 **UI를 두 번 만든다.** 위 3개가 정확히 그 경계다.

### 단계

| Phase | 내용 | 세션 | 매매 영향 | 언제 |
|---|---|---|---|---|
| **A** | SQLite / DPAPI / 싱글톤 / 종가베팅 폴백 구분 / 라이선스 | **6~8** | **없음** ✅ | **지금 바로** — 미검증 6건과 안 겹침 |
| **B** | 계약 3개 확정(설정 스키마·DB 스키마·L2 경계) + 코드사이닝 결정 — **문서 작업** | **1~2** | 없음 | A와 병행 가능 |
| **C** | 상수 분리 + 설정 외부화 + 테스트 389곳 | **4.5~6** | **있음** ⚠️ | **미검증 6건 정리 후** |
| **D** | L2 패키징 + 배포본 스모크 테스트 | **6~10** | 없음 | C 이후 |
| **E** | UI 10화면 + 조건식 3중 방어 + 에러 번역 | **9~12** | 없음 | D와 병행 가능 |
| **F** | 설치 프로그램 + 자동 업데이트 + 온보딩 문서 + 베타 | **5~10** | 없음 | 마지막 |

**Phase A가 핵심이다.** 6~8세션이 매매에 전혀 안 닿으면서 제품화의 3분의 1을 끝낸다.
지금 실전 봇의 미검증 변경을 관찰하는 동안 병렬로 진행할 수 있어 **일정상 공짜다.**

Phase A 안에서는 **SQLite 전환이 가장 크고 되돌리기 쉬워서** 첫 작업으로 적당하다.
